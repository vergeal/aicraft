# 运维知识库标准

知识库是「已经验证过的结论」的集合，不是聊天记录的副本。入库、去重、检索都由本目录的代码执行，本文是它的文字标准：改判定先改这里，再改 `schema.ts` / `search.ts`，两边不得各说一套。

## 存储

位置固定在插件数据目录下：

```text
<plugin data>/hyt/knowledge/
  index.json            权威索引：{ version: 1, updatedAt, entries: KnowledgeEntry[] }
  entries/<id>.json     单条明细，便于人工查看、迁移与排障
```

- 读取只信 `index.json`；`entries/` 下的单条文件损坏或被删不影响检索。
- 写入时两份一起更新，先写索引再写明细，两者都用「临时文件 + rename」替换，进程崩溃不会留下半截 JSON。
- 条目量按几千级设计：每次检索对全量条目现场打分，不维护持久化倒排索引。

## 条目结构

```jsonc
{
  "id": "kb_<uuid>",
  "kind": "qa",              // qa | faq | runbook | doc
  "title": "登录失败怎么处理", // 省略时取问题或正文前 40 字
  "question": "为什么登录一直失败", // 可选；同问题判定优先用它
  "answer": "先检查账号是否被锁定……",
  "tags": ["登录", "账号"],
  "source": "manual",        // manual | doc | history | mcp
  "confidence": 0.9,         // 0..1
  "createdAt": "2026-11-22T08:00:00.000Z",
  "usedCount": 0,
  "lastUsedAt": "2026-11-22T08:00:00.000Z"
}
```

`kind` 的用法：

| kind | 用于 |
| --- | --- |
| `qa` | 一问一答，默认值 |
| `faq` | 常见问题，答案偏简短 |
| `runbook` | 有步骤的处置手册 |
| `doc` | 从 md / txt 导入的整篇资料 |

`source` 记录来源渠道：`manual` 手动或模型写入，`doc` 本地文档导入，`history` 从聊天记录提炼，`mcp` MCP 检索结果（默认不落库）。

## 入库门槛

一条内容必须同时满足以下条件才会进入 `addKnowledge`：

1. **置信度 ≥ 0.8**。低于门槛的内容可以出现在对话里，但不入库。
2. **不是寒暄**。归一化后整句等于「你好 / 在吗 / 收到 / 谢谢 / hi / ok」等固定寒暄，或长度不超过 12 个字的寒暄变体。
3. **不是纯表情**。去掉表情后没有剩下任何内容。
4. **不是纯链接**。去掉 URL 与分隔标点后不剩文字；带结论的链接可以入库。
5. **有效内容不少于 8 个字**。问题与答案归一化后合计长度不足 8 字，视为没有可复用信息。

拒绝时返回原因，`hyt.knowledge.add` 会把原因原样告诉模型。规则实现在 `checkAdmission`，寒暄表是 `GREETINGS`。

## 去重与合并

入库前先用问题和标题找重复：

- 归一化：全角转半角、去空白与标点、英文小写。
- 判定：完全相同，或 2-gram Dice 相似度 ≥ `0.8`。
- **同一问题不新增条目**，而是合并进旧条目：
  - `answer` 用新答案覆盖；
  - `tags` 取并集，最多 8 个；
  - `confidence` 取两者较高值；
  - `usedCount + 1`，`lastUsedAt` 更新；
  - `kind` / `title` / `source` 以新值为准，新值为空时保留旧值。

「同一个问题被不同人问第二次」应当是旧条目变强，不是知识库里多一条几乎一样的记录。

## 检索

`searchKnowledge` 一次对全部条目打分：

- 中文按 2-gram 切分，英文和数字按整词；标点与空白不参与。
- 打分用 BM25（`k1 = 1.2`、`b = 0.75`），索引字段为标题、问题、答案和标签的拼接。
- 只返回得分大于 0 的条目，按得分降序，默认取前 5 条。
- 命中并实际被引用的条目由 `recordUsage` 记录，用于之后按使用次数排序与淘汰。

检索是纯函数（`search`），可以脱离磁盘单独测试。

## MCP 知识来源

`hyt` 设置里的 `mcpKnowledgeTools` 登记形如 `server.tool` 的工具名。适配器在 `mcp.ts`：

- 检索时以 `{ query, limit }` 调用登记的工具；
- 兼容数组、`results` / `items` / `data` 包裹、纯文本三种返回；
- 映射出的条目 `source = mcp`、`confidence` 默认 `0.6`，低于入库门槛，因此只参与当次检索，不会自动写入知识库；
- 调用失败按「没有结果」处理，不影响本地检索。

当前只提供适配器与映射，实际调用 MCP 工具的接线留给上层会话。

## 导入本地文档

`importKnowledge(root, directories, now)` 扫描设置里 `knowledgePaths` 指定的目录（递归 4 层，只收 `.md` / `.markdown` / `.txt`）：

- 标题取第一个一级或二级 Markdown 标题，没有则用文件名；
- 正文保留全文，单篇截断到 20,000 字；
- 行内 `#标签` 会被收集为标签，最多 8 个；
- 与手动入库走同一套门槛和合并规则，重复文件按标题合并。

## 维护

- 导出：`exportKnowledge(root)` 返回完整的 `index.json` 文本，可直接备份或迁移。
- 删除：`removeKnowledge(root, id)` 同时删索引项与单条文件。
- 人工修复：确认索引损坏时，可以从 `entries/*.json` 重建 `index.json`，字段结构就是上面的条目结构。
- 不要把聊天原文直接批量写进知识库；从历史提炼的条目应经过模型归纳，并以 `source = history` 标注。
