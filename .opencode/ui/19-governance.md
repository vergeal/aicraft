# 19 · 治理与版本化

## 1. 单一真源

| 内容 | 真源 | 产出 |
|---|---|---|
| 色值、尺寸、字号 | token 定义文件 | CSS 变量 / 设计工具库 |
| 组件规格 | 组件源码 + 本文档 | 文档与实现必须一致 |
| 图标 | sprite 源文件 | 运行时 symbol |
| 文案 | 文案表 | 界面与原生菜单 |

**禁止**在文档里手抄数值后不回写代码。文档与代码不一致时，以代码为准并立刻修文档——否则三个月后文档就成了谣言。

## 2. 命名规范

```
--{层}-{类别}-{语义}[-{状态}]

--p-blue-500                原始层：色名 + 档位
--c-text-secondary          语义层：类别 + 语义
--c-border-strong           语义层：类别 + 强度
--c-bg-layer-2              语义层：类别 + 层级
--density-control-h         系统层：维度参数
```

| 规则 | 说明 |
|---|---|
| 语义层不带颜色名 | `--c-danger` ✓ / `--c-red` ✗ |
| 不出现像素值 | `--r-md` ✓ / `--r-12` ✗（改值不必改名） |
| 状态后缀固定 | `-hover` `-active` `-disabled` `-selected` |
| 层级用数字 | `layer-1/2/3`，不用 `low/mid/high` |
| 一个 token 一个职责 | 不复用"看起来差不多"的 token |

## 3. 新增 token 的门槛

新增前必须四问全过，否则用现有 token 组合：

1. **已有的语义 token 真的表达不了吗？**（多数情况是组合问题）
2. **它在两个主题下都有值吗？**（单主题 token 一律驳回）
3. **它的名字能脱离上下文被理解吗？**（不能就是命名没想清）
4. **三个月后它能被安全删除吗？**（说不清用途的就是死 token）

## 4. 废弃流程

```
标记 → 迁移 → 观察 → 删除
  ↓       ↓       ↓       ↓
加注释   改调用方  一个有版本周期  移除
```

| 阶段 | 动作 | 时长 |
|---|---|---|
| 标记 | 注释写 `@deprecated 用 --c-x 替代`，不改名 | — |
| 迁移 | 全量改调用方，保留旧 token 指向新值 | 1 个版本周期 |
| 观察 | 确认无引用（grep + 构建检查） | 1 个版本 |
| 删除 | 移除定义，更新文档变更记录 | — |

**不要一步删除**：跨仓库/跨端（设计工具）常有滞后引用。

## 5. 版本语义

| 变更 | 版本 | 举例 |
|---|---|---|
| 新增 token / 新增组件 | minor | 新增 `--c-warning-soft` |
| 只改数值（视觉微调） | patch | `--r-md: 12 → 14` |
| 删除 token、改语义 | **major** | `--c-text-secondary` 含义变化 |
| 重命名 | **major**（等价于删+增） | — |

major 变更必须附迁移指南，且在设计评审里单独过一遍。

## 6. 变更记录（ADR 精简版）

每篇一个文件，模板：

```markdown
## D-012 主按钮改用黑白填充

- 日期：2026-11-18
- 状态：已采纳 / 试用 / 已废弃
- 影响面：按钮、所有主操作入口

### 背景
品牌色按钮在深色主题下需要单独提亮，导致两套色值难以同步。

### 决策
主操作统一使用黑/白填充，品牌色只用于链接与指示。

### 代价
品牌识别度下降；需在插图与加载态补足品牌感知。

### 备选
1. 保持品牌色 + 深色主题单独提亮（已否决：维护两套值）
2. 品牌色仅用于悬停（已否决：状态色不稳定）
```

**只记录"做过的取舍"**，不记录"做了什么组件"——后者文档已经写了。

## 7. 评审流程

| 变更类型 | 需要谁 | 检查项 |
|---|---|---|
| 新增组件 | 设计 + 前端 + 可访问性 | 规格齐全、四态齐备、键盘可达 |
| 修改样式 | 前端自查 + 一次抽查 | 走 [checklist](checklist.md) |
| 修改 token | 设计 + 前端共同 | 两主题都有值、影响面列全 |
| 新增图标 | 设计 | 网格/描边一致、命名合规 |

评审**只对照 checklist 与本文档条款**，不对照个人审美。有分歧时先补一条规则，再决定实现。

## 8. 度量

| 指标 | 目标 | 采集方式 |
|---|---|---|
| 硬编码色值数 | 0 | 静态扫描十六进制 |
| 非阶梯间距数 | < 5% | 扫描 px 字面量 |
| 缺四态的交互组件 | 0 | 组件清单核对 |
| token 采纳率 | > 90% | 引用 token 的声明占比 |
| 文档与代码差异 | 每版本重建一次 | 从代码重新生成 token 表并 diff |

## 9. 腐化信号

出现以下任一情况，说明系统正在失效：

1. 出现"临时决定，下次改"的样式，且没有记录。
2. 同一个视觉问题在两个组件里用了两种解法。
3. 有人开始直接写色值"因为 token 对不上"。
4. token 数量增长速度超过组件数量增长速度。
5. 文档最后一次更新早于最近两个版本。

## 10. 落地规则

1. 文档与实现不一致时以代码为准，并立刻修文档。
2. 新增 token 必须通过四问。
3. 删除/重命名走 major 版本 + 迁移指南。
4. 每个取舍写一篇 ADR，只写取舍不写功能。
5. 评审只对照条款，不对照审美。
6. 每版本从代码重新生成 token 表并 diff。
